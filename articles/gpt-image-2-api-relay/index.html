gpt-image-2 生图 API 中转：从调通到能批量跑，中间那几道坎

models2026-11-09·gpt-image-2 API

文本模型的接入经验，搬到图像上有一半不适用。端点不同、计费不同、返回不是流、任务是异步或长耗时、失败原因经常藏在请求体里。这篇把踩过的几道坎按顺序列出来。

端点和文本模型不是一套

聊天补全走 /v1/chat/completions，图像生成通常走 /v1/images/generations。用 OpenAI SDK 的话：

from openai import OpenAI

client = OpenAI(
    api_key="sk-你的令牌",
    base_url="https://token173.net/v1",
)

r = client.images.generate(
    model="gpt-image-2",
    prompt="干净的浅色背景，一只陶瓷杯放在木桌上，柔和侧光，产品摄影",
    size="1024x1024",
    response_format="url",
)
print(r.data[0].url)

几个参数值得提前确认，因为各家聚合平台实现程度不同：

  • size：支持的尺寸列表不一样，有的只收固定几档，传自定义尺寸直接 400。
  • response_format：url 还是 b64_json。批量场景下 b64 会让响应体暴涨，也容易撞网关的响应大小限制。
  • n：一次出几张，部分通道限 1。
  • 图生图、多图合成这类能力一般走 extra_body 传图片，属于平台扩展，不是标准字段，得看文档。

gpt-image-2-d 属于同族变体，具体差异（速度、尺寸、编辑能力）以控制台模型说明为准，别凭后缀猜。真要选，拿同一组 prompt 各跑十张，出图稳定性和单张耗时一比就清楚。

计费逻辑和文本完全不同

文本按输入 / 输出 token 算，图像多数按次、按尺寸档位，甚至按质量档算。拿「每百万 token 多少钱」去估生图预算，一定错得离谱。

要提前问清楚或自己测出来的：

  1. 失败请求计不计费（生成被内容策略拦下、超时、参数错误）。
  2. 一次 n=4 是按一次还是按四张计。
  3. 重试是否另算 —— 长耗时任务里客户端超时自动重试，最容易在这里翻倍。
  4. 图片 URL 的有效期，过了要不要重新生成或重新取。
  5. 用量明细里能不能把图像任务和文本任务分开导出。

第 5 项在做成本归集时特别实用。我一般把生图单独建一个 Key，月底导账单时不用再从一堆 chat 请求里挑。

国内直连下的两个具体麻烦

上传体积。 图生图要传原图，base64 编码后大约膨胀三分之一。中转节点、反向代理、上游网关任何一层有 client_max_body_size 或请求体超时，都会在前半段失败，而且错误经常是含糊的 413 或连接重置。能传 URL 就别传 base64，能压就压，但别把分辨率压到模型看不清参考细节。

等结果别用同步思维。 图像生成十几秒到几十秒很正常，视频更长。客户端读超时按文本聊天设的 30 秒，会把正常任务判成失败，然后触发重试 —— 上游那次其实已经生成完并计费了。图像任务的读超时单独放宽到 120 秒以上，重试上限设 1，并且在重试前先查一次任务状态。

一次典型的排错顺序

现象先查什么
404 model not found从 /v1/models 复制 ID，gpt-image-2-d 这类变体最容易手打错
400 invalid size / parameter尺寸档位、response_format、平台是否支持该扩展字段
413 / 连接重置请求体大小、图片 base64、代理层限制
超时但账单已扣客户端读超时、自动重试、任务是否已提交成功
返回 URL 打不开URL 有效期、是否需要带鉴权、对象存储域名是否可达
出图质量不稳定固定 prompt 跑十张，看是模型波动还是被路由到了不同通道

最后一条容易被忽略：同一个模型 ID 后面可能挂了多条上游线路，质量不一致时，看后台调用记录里有没有通道信息，比反复调 prompt 有用。

批量跑之前先做这几件事

  • 固定一组 20 条 prompt，覆盖中文、英文、含品牌词、含人物、含文字排版，跑通再放量。
  • 并发从 2 起步，往上加时盯 429 和排队行为，别一上来开 50。
  • 生成结果落自己的对象存储，不要依赖平台返回的临时 URL 做长期资产。
  • 单建 Key、单设额度上限，生图任务失控时烧钱比文本快得多。
  • 记录每条任务的 request_id、prompt、尺寸、耗时、扣费，后面核对和质量复盘都要用。

平台这块

我这轮是在 token173.net 上跑的，主要是它的控制台把 gpt-image-2、gpt-image-2-d 和文本型号归在同一个 Key 下，做「先用文本模型把 prompt 润色、再交给生图、最后用文本模型批量写图注」这条链时，不用在两套账号之间倒来倒去，账单也在一起。国内直连，人民币结算。

它同样是托管中转，上传的参考图和生成结果都会经过第三方服务器。涉及未发布产品图、客户素材、含个人信息的图片，别走公共链路，这条边界跟用哪家无关。

收尾

生图接入的技术难点从来不在那条 images.generate，在超时、重试、体积、计费口径和结果落地。把这五样理顺，剩下的就是老老实实跑样本。型号 ID、尺寸档位和价格会调，接之前拉一次 /v1/models，再看价格页当前口径。
